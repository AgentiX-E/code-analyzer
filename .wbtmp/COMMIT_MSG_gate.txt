fix(languages): the comment capture is kept, because the reason for dropping it is false

**`attachDocCommentsInOrder` dropped every `DOCSTRING`/`COMMENT` capture after using it as the next declaration's
docstring**, and the code gave its reason: *"Comments are not symbols and are dropped here, which is also what keeps
them out of the graph: ... nothing downstream wants them as declarations."*

## The second clause does not hold

`groupCaptures` builds a **symbol** only from a `*_DEF` tag and a **reference** only from a call or import tag, so a
`DOCSTRING` or `COMMENT` capture produces **neither**. **It was never in the graph, and removing it could not keep it
out of one.** Dropping it was justified by a mechanism that does not exist.

## And it broke a contract two consumers state

`ParsePhase` skips nameless captures on purpose - *"(e.g. regex docstring/decorator captures), which cannot be
export-checked"* - and its guard asserts that such a capture survives. **Twenty-three tests pin `parse()`'s output
across thirteen provider files plus `phases-execution`, and every one of them has been red since `3af69dd` dropped the
capture** - because that change was verified against the one new file it added rather than against the suite.

## The association and the capture are independent, and both are kept

The comment still becomes the next declaration's `docstring`; it is also still returned as a capture. **Thirteen tests
returned to green without being edited**, and nothing observable downstream moves, because nothing downstream ever
read the capture.

## And three stale-representation families alongside it

- **`14b4a13` changed `generateEmbeddings`' return shape** to `{ results, backend, reason }`, which is what
  `embed.ts:252` destructures and what `embedding-backend.yml` reads to refuse a `none` figure. **Fifteen tests
  expected an array; they now destructure `.results`.**
- **A hard-coded MCP tool count.** The doc/code gate reports `mcpToolCalls: 49, failures: []`, so the committed
  documents already agree with the committed code and only the literal `48` inside the test was stale.
- **`scripts/lint-baseline.json` is regenerated.** `b0b4898` fixed `parserOptions.project` so the package test
  directories are genuinely linted; before it, typed linting reported a **parse error** per file and the baseline
  recorded `1` for most of the suites. **356 -> 413 files, 702 -> 5722 findings, 269 files up.** The rise is the
  suites' pre-existing debt with a number on it, not a lowered bar.
